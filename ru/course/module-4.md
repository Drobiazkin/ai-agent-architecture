# Модуль 4 — Агенты и оркестрация: детализация

*Спутник «Модуля 4». Язык — Java без агентных фреймворков: весь смысл модуля — построить харнесс (§10.2 книги) самому, чтобы потом видеть его внутри любого фреймворка.*

## 4.1 Свой харнесс: ReAct-цикл

Контракт инструмента и ядро цикла (~150 строк вместе с парсингом; каркас):

```java
public interface Tool {
    String name();
    String description();               // это читает МОДЕЛЬ — контракт ACI, §12.3 книги
    String execute(Map<String, String> args);
}

public final class AgentHarness {
    private final ChatClient chat;
    private final Map<String, Tool> tools;
    private final int maxSteps;         // бюджет итераций — §10.5, без него цикл не терминируется

    public String run(String task) {
        var transcript = new StringBuilder(task);
        for (int step = 0; step < maxSteps; step++) {
            String out = chat.prompt().system(REACT_SYSTEM)     // формат: Thought / Action / Final
                             .user(transcript.toString()).call().content();
            var action = parseAction(out);                       // Action: tool_name({"k":"v"})
            if (action.isEmpty()) return parseFinal(out);        // модель дала финальный ответ
            Tool tool = tools.get(action.get().name());
            String observation = (tool == null)
                ? "ERROR: нет инструмента " + action.get().name()  // ошибку — В КОНТЕКСТ (§12.4)
                : safeExecute(tool, action.get().args());          // try/catch + тайм-аут внутри
            transcript.append("\n").append(out)
                      .append("\nObservation: ").append(observation);
        }
        throw new BudgetExceededException("шагов > " + maxSteps); // эскалация, не молчание
    }
}
```

REACT_SYSTEM пишешь сам по §13.3 книги (формат Thought→Action→Observation, список инструментов с описаниями, требование «одно действие за ход»). Инструменты для старта: `search_kb` (обёртка над ретривом М3) и `get_order_status` (заглушка с фиксированными данными).

Что заметить, пока пишешь: *весь* детерминизм — твой (парсинг, диспетчеризация, бюджеты, тайм-ауты), модель только предлагает следующий шаг. Это и есть «агент = LLM-ядро + харнесс».

## 4.2 Лимиты и детекция прогресса (§10.5)

Сигнатура шага — инструмент + хэш нормализованных аргументов; повтор = отсутствие прогресса:

```java
record StepSignature(String tool, String argsHash) {}

private final Deque<StepSignature> recent = new ArrayDeque<>(3);

boolean isStuck(StepSignature s) {
    boolean repeat = recent.contains(s);
    if (recent.size() == 3) recent.removeFirst();
    recent.addLast(s);
    return repeat;
}
```

Хэш — по аргументам с сортировкой ключей и trim строк (иначе `{"id":"123 "}` и `{"id":"123"}` — «разные» шаги). Тест на нетерминацию: инструмент-заглушка всегда возвращает «данных нет, попробуйте ещё раз» — агент обязан остановиться с эскалацией за ≤ maxSteps, а факт остановки по прогрессу (не по бюджету) — отдельным полем результата.

## 4.3 Orchestrator-Workers с дисциплиной саги (§11.5)

Своя таблица саг (проще и прозрачнее eventuate-tram для учебных целей; он остаётся опцией):

```sql
CREATE TABLE saga_steps (
    saga_id     uuid    NOT NULL,
    step_no     int     NOT NULL,
    step_key    text    NOT NULL,      -- ключ шага: saga_id + семантика шага; тот же ключ уедет на побочный эффект
    status      text    NOT NULL CHECK (status IN ('STARTED','DONE','COMPENSATED')),
    payload     jsonb,
    updated_at  timestamptz DEFAULT now(),
    PRIMARY KEY (saga_id, step_no),
    UNIQUE (step_key)                  -- журнал не двоится: одна строка журнала на шаг
);

-- Таблицу заводит владелец (assistant), но ходит по ней приложение — а оно с §3.3 М3 подключается
-- только под app_user. Грант стоит рядом с DDL по правилу §3.2 М3: таблица без гранта для
-- приложения не существует. Журнал воркер и пишет, и перечитывает при рестарте — отсюда три права:
GRANT SELECT, INSERT, UPDATE ON saga_steps TO app_user;
```

Ключ шага несёт **само действие**, а не журнал. Книга ставит его именно туда: §10.4 — «шаг повторяется, побочный эффект не должен дублироваться → идемпотентные операции по ключу»; §11.5 — «идемпотентность воркер-шага по ключу задачи»; Прил. D — «действия агента идемпотентны по ключу операции». `UNIQUE` на `saga_steps` запрещает дубль *строки журнала* — от второй заявки он не спасает. Поэтому тот же `step_key` едет в таблицу заявок (саму таблицу заводит DDL ниже; строки в ней создаёт сага, и из неё же М5 берёт заявки для code mode):

```sql
CREATE TABLE tickets (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    step_key    text    NOT NULL UNIQUE,   -- ТОТ ЖЕ ключ шага: дубль заявки отсекается ЗДЕСЬ, а не в журнале
    category    text    NOT NULL,
    summary     text    NOT NULL,
    status      text    NOT NULL DEFAULT 'OPEN',
    created_at  timestamptz DEFAULT now()
);

-- То же правило (§3.2 М3): грант рядом с DDL. Отдельный грант на sequence identity-колонке
-- не нужен — она обслуживается правом INSERT на саму таблицу. Проверено на стенде.
GRANT SELECT, INSERT, UPDATE ON tickets TO app_user;
```

Ключ обязан доехать до эффекта через **сигнатуру инструмента**, иначе звено рвётся молча. Заявку создаёт `createTicket`, а на сборке М8 (§8.1, шаг 2) этот вызов идёт уже *только* через MCP-клиент к серверу М5 — вывести ключ на стороне сервера нечем, он про шаг саги ничего не знает. Поэтому контракт — `createTicket(category, summary, stepKey)` (М5 §5.1 держит ту же тройку). Имя пишется по-разному с двух сторон, и это не расхождение, а две разные конвенции: `stepKey` — параметр Java-метода, он же уезжает в схему инструмента и на провод MCP; `step_key` — колонка в SQL. Идемпотентность живёт **внутри** инструмента:

```sql
INSERT INTO tickets (step_key, category, summary) VALUES (?, ?, ?)
ON CONFLICT (step_key) DO NOTHING RETURNING id;  -- ничего не вернулось → заявка уже есть:
SELECT id FROM tickets WHERE step_key = ?;       --   вернуть её id, второй заявки не создавать
```

`step_key` проставляет **воркер**, а не модель: он детерминирован (`saga_id` + семантика шага), и харнесс подставляет его перед вызовом, затирая то, что модель написала в этом поле. Модель не выдумывает ключи идемпотентности — на повторе шага она выдумает новый, и вторая заявка пройдёт как первая.

Оркестратор (LLM) порождает план; каждый шаг воркера исполняется по протоколу: `INSERT ... STARTED ON CONFLICT (step_key) DO NOTHING` в журнал → `createTicket` с тем же `step_key` **в своей транзакции** → `UPDATE ... DONE` с результатом в `payload`. Разрешение при рестарте — по журналу: `DONE` → шаг закончен, результат в `payload`; строки нет → шаг не начинался; `STARTED` → **неизвестно** (эффект мог успеть, а мог и нет), и воркер просто повторяет шаг — неизвестность разрешает ключ на действии, а не журнал. Компенсация — обход DONE-шагов в обратном порядке с вызовом их компенсирующих операций.

**Хаос-эксперимент (chaos engineering / fault injection):** точка убийства — *после* побочного эффекта, *до* `DONE`:

```java
// fireOnce = AtomicBoolean.compareAndSet(true, false): взводится тестом, срабатывает ОДИН раз
if (chaos.fireOnce("worker-after-effect")) throw new SimulatedCrashException();
```

**Одноразовость инъекции — условие выполнимости теста (1), а не деталь реализации.** Первый прогон умирает после эффекта, второй проходит точку насквозь и доводит сагу до `DONE`. Оставишь флаг постоянно взведённым — второй прогон умрёт там же, `UPDATE ... DONE` не выполнится никогда, `payload` останется `NULL`, и вторая половина теста (1) («сага доезжает до конца») недостижима при любой корректной реализации протокола.

**Границы транзакций — предусловие эксперимента, а не деталь.** Заявка обязана коммититься **отдельно** от `UPDATE ... DONE`. Положишь эффект и журнал в одну транзакцию — `SimulatedCrashException` откатит оба: рестарт увидит чистое состояние, `UNIQUE` не сработает ни разу, тест (1) станет зелёным, не проверив ничего. Окно между коммитом эффекта и коммитом `DONE` — это и есть то, что хаос-тест обязан воспроизвести; закрыть его транзакцией нельзя (заявка живёт в БД, а в общем случае — за сетью), поэтому его закрывают ключом.

Два автотеста: (1) докат вперёд — после двух прогонов (первый убит в точке инъекции, второй прошёл её насквозь) `SELECT count(*) FROM tickets WHERE step_key = ?` возвращает 1 (дубль отсекается `UNIQUE` в `tickets`, не в журнале), а сага доезжает до конца с непустым `payload`; (2) откат — компенсации выполнились для всех DONE-шагов, состояние домена вернулось. Оба зелёные = DoD-пункт.

## 4.4 Human-in-the-Loop Gate (§10.6)

Реализация по карточке книги: таблица `pending_actions` (что/почему/предпросмотр/deadline), эндпоинт очереди ревью, решение оператора, **безопасный тайм-аут** (нет решения к deadline → отклонить, не исполнить). DDL пишешь сам, но грант к нему — по тому же правилу §3.2 М3, сразу и рядом: `GRANT SELECT, INSERT, UPDATE ON pending_actions TO app_user;` — очередь читает и пишет приложение, а оно ходит только под этой ролью. Метрики гейта — в те же спаны Langfuse: доля одобрений, медианное время решения.

**Эксперимент automation complacency** (Parasuraman & Riley, 1997; разговорно — rubber-stamping): одобри 30–50 действий подряд не глядя, со случайными паузами 1–3 с. Алерт обязан сработать по паре сигналов «доля одобрений → 100% при времени решения → секунды». Если не сработал — теперь ты знаешь почему (пороги? окно агрегации?), чини и повторяй: это упражнение на *метрику*, а не на дисциплину оператора.

## 4.5 Workflow против агента (§10.3, §11.8)

Одна задача («заявка на возврат: проверить заказ → проверить регламент → создать заявку») в двух исполнениях: фиксированная цепочка из трёх вызовов и твой агент из §4.1 с теми же инструментами. По 20 прогонов: стоимость, латентность, доля успеха, дисперсия числа шагов. Таблица + вывод для прода — в мини-ADR (подсказка из книги: большинство «агентов» в проде — workflow с одной-двумя точками автономии).

## 4.6 Разбор отказов по MAST (§14.4)

Вытащи из Langfuse три сбойные траектории (после §4.2 и §4.3 они у тебя есть) и классифицируй по таксономии MAST: этап (спецификация / межагентное рассогласование / верификация), конкретная категория, что бы поймало раньше — спецификация, гейт или eval. Полстраницы на траекторию; это заготовка культуры пост-мортемов для М6.
