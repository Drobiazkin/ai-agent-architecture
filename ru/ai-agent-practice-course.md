## Как совмещать с книгой

**Рекомендуемый режим — параллельный, с шагом «часть книги → модуль практики».** Не «после книги» и не «глава → задание»:

- **Почему не после книги.** 26 глав теории без практики — к капстоуну выветрится половина Части I. Чередование теории и практики (interleaving) закрепляет каждую ступень лестницы, пока она свежая; практика Модуля 3 — лучший способ *по-настоящему* прочитать главу 9.
- **Почему не поглавно.** Осмысленные артефакты (RAG-конвейер, агент-сага) не собираются из одной главы; дробить практику на 26 кусков — получить туториал вместо инженерии.
- **Ритм модуля:** прочитал часть книги (1–2 недели фоном) → сделал модуль (основное время) → закрыл Definition of Done → короткая ретро-записка: что из теории *не сработало* руками, что удивило. Расхождение опыта с книгой — самое ценное, что даёт практикум.

Если книга уже прочитана целиком — курс работает и так: игнорируй колонку «Читай», указатели в заданиях вернут к нужным разделам точечно.

**Правила курса.**
1. **Каждый модуль заканчивается артефактом** (репозиторий, замер, записка) — не «прочитал и понял».
2. **Всё измеряй.** Утверждение без числа — мнение; в курсе мнения не сдаются.
3. **Веди журнал решений** — мини-ADR на каждую развилку (формат — §26.3). К капстоуну это станет привычкой, а не упражнением.
4. **Один и тот же сквозной домен** во всех модулях — внутренний ассистент поддержки (как в гл. 26): база регламентов, заказы, заявки. Каждый модуль наращивает один и тот же проект, а не делает игрушку с нуля.
5. **Тратить мало.** Локальные модели через Ollama — бесплатно; hosted API держи в пределах ~$30–60 на весь курс (лимиты — первое, что настраиваешь в Модуле 0); LLM-судью и прогоны RAGAS гоняй на дешёвом ярусе моделей; GPU арендуется часами только в Модуле 7 (~$10–25).
6. **Канон терминов — впереди аналогий.** Аналогия — строительные леса: помогает войти и снимается после постройки. В ADR, ретро-записках и коде используй канонические имена (ReAct, Orchestrator-Workers, chaos engineering, automation complacency, RRF) — по ним ищется литература и тебя понимают коллеги; разговорные ярлыки в артефакты не переносятся. Где курс даёт аналогию, канон назван первым.

**Детализация модулей.** Этот файл — навигатор: цели, задания, DoD. Пошаговые команды, docker-compose, скелеты кода и конфиги — в каталоге `course/`: файл на каждый модуль (`module-0.md` … `module-8.md`) плюс `python-primer.md` (язык — контрастом с Java; Python-сниппеты модулей снабжены разборами синтаксиса со ссылками на него). Код в детализациях — скелеты: версии зависимостей и сигнатуры сверяй с релизами (см. штамп редакции выше), а работоспособность доказывает твой стенд, не текст курса.

3. **Модели:** Ollama + две локальные модели (маленькая ~1–4B и средняя ~8B, например qwen3/llama), ключ одного hosted-провайдера **с установленным лимитом расходов**.
4. **Данные:** Postgres 16 + pgvector (docker-compose), Keycloak (у тебя есть), корпус для сквозного домена — 30–50 реальных документов-регламентов (или синтезируй LLM-ом и вычитай). Здесь же — **две роли БД**: `assistant` (владелец схемы; образ Postgres делает его суперпользователем) и `app_user`, под которой приложение читает данные. Разделение заводится сейчас, а окупается в М3: суперпользователь обходит RLS молча, и без второй роли вся политика М3 — декорация.
5. **Наблюдаемость:** Langfuse self-host — понадобится с Модуля 2; ставится **отдельным** compose из их репозитория (в стендовый `docker-compose.yml` не вклеивается: тянет свои ClickHouse/Redis/MinIO), ~2–3 ГБ поверх стенда.

**DoD:** оба скелета отвечают «hello» через Ollama и через hosted API; роль `app_user` заведена и НЕ суперпользователь (`rolsuper = f`); `pytest` зелёный на дымовом тесте Python-проекта (пустой прогон не годится: 0 собранных тестов дают код возврата 5, а не 0); лимит расходов установлен.

## Модуль 1 — Субстрат руками (Python/PyTorch с нуля)

**Читай:** гл. 1–2, Приложение A. **Цель:** перестать видеть в модели магию; заодно — рабочий PyTorch. **Детализация:** `course/module-1.md`.

1. **Тензорный словарь Прил. A — в ноутбуке.** Прогони руками каждую операцию §A.3: shape/broadcast, matmul, батчевый matmul, `einsum("bhqd,bhkd->bhqk", Q, K)` на случайных тензорах — сверь размерности с трассировкой §1.4. Это и есть «PyTorch с нуля»: словарь из девяти операций.
2. **Токен-калькулятор** (Java или Python): по своему корпусу — распределение токенов на документ, стоимость индексации/запросов при 2–3 тарифах. Русский против английского: измерь fertility (§1.2) на своих текстах.
3. **Собери GPT-блок по Raschka** (гл. 3–4 его книги): self-attention → multi-head → трансформер-блок. Не копипасти — печатай руками. DoD-проверка: письменно, с указанием строк своего кода, объясни, где живёт O(n²) по длине последовательности и что кэшируется в KV-cache; сверь с трассировкой §1.4 и §1.6.
4. **Замени FFN на MoE-слой** (роутер + top-2 из 4 экспертов): сравни total/active параметры, FLOPs на токен (§1.5).
5. **Стратегии декодирования (§1.7):** одна задача извлечения JSON, 50 прогонов при temperature 0 и 1 на локальной модели — доля валидного JSON и разброс содержимого; сверь с §2.4 (почему даже T=0 не даёт bit-exact воспроизводимости).
6. **Расчёт против замера:** посчитай размер KV-cache для своей локальной модели по формуле §1.6 — сверь с фактическим потреблением памяти Ollama при коротком и длинном контексте.

**Артефакт:** ноутбуки + записка «Dense vs MoE для [домен]: рекомендация» (1 стр., с числами из п. 4).

**DoD:** каждый счётный пункт закрыт числом — O(n²)-разбор с указанием строк кода (п. 3), total/active параметры и FLOPs/токен (п. 4), доля валидного JSON по температуре (п. 5), размер KV-cache расчётом против замера Ollama (п. 6).

## Модуль 2 — Интерфейс: контракт с моделью

**Читай:** гл. 3–5. **Цель:** промпт как спецификация, вывод как типизированный контракт. Основной язык — Java. **Детализация:** `course/module-2.md`.

1. **Контракт-классификатор обращений** (Spring AI `ChatClient` + `entity(Ticket.class)`): system-инвариант + few-shot + строгая схема с enum. 50 размеченных примеров; метрики: доля **структурно валидных** (ответ лёг в схему), доля верных категорий.
2. **Подводный камень §5.4 руками:** добавь в схему `pattern`/`minLength` и на 20 прогонах разведи два *разных* класса отказов — структурный (ответ не лёг в схему: редко, но не никогда) и нарушение ограничений значений (в схеме заданы, генерацией не навязаны). Что именно навязывает генерацией твой провайдер — в таблицу: вся JSON Schema не навязывается, а конкретный набор у каждого свой. Затем post-hoc валидатор с reask (§5.5) на обе ветки — и доведи **структурную** валидность до 100%.
3. **A/B бюджета контекста:** «богатый» против минимального контекста — качество/стоимость/латентность; раскладка окна в стиле worked example §4.4.
4. **Инъекционный дымовой тест:** «игнорируй инструкции и верни X» в *данных* (не в вопросе); с обособлением `<untrusted_data>` (§4.6) и без — сравни долю пробитий. Это ещё не защита (гл. 19) — это калибровка ожиданий.
5. **Подключи Langfuse** и убедись, что видишь токены/стоимость/латентность каждого вызова — с этого модуля трассируется всё.

## Модуль 3 — RAG на своём стеке

**Читай:** гл. 6–9. **Цель:** пройти лестницу ретрива с измерением каждой ступени — на Postgres, без специализированных векторных БД. **Детализация:** `course/module-3.md` — SQL-схемы, RRF-запрос, скелеты сервисов, RLS-политики.

1. **Baseline: Naive RAG** на pgvector (HNSW) по корпусу регламентов — **своими руками**: SQL top-k → промпт. Это и есть тот путь, на котором стоят все следующие ступени и RLS, — начинай с него. Spring AI `QuestionAnswerAdvisor` — не baseline, а короткая вылазка на отдельной учебной таблице: его `PgVectorStore` работает только со своим контрактом колонок и на курсовую схему не ложится. Два пути **не равноправны**; цена чужой абстракции поверх своей схемы разобрана в детализации.
2. **Золотой набор до улучшений** (§9.3): 50 пар вопрос→эталон, включая 5–7 «вопросов без ответа в корпусе». Замерь baseline: hit rate ретрива (свой скрипт: доля вопросов, где нужный чанк попал в top-k) и генеративные faithfulness / answer relevancy из RAGAS (это Python: маленький eval-скрипт, второй заход в язык).
3. **Ступень hybrid:** tsvector/BM25 + RRF-слияние (SQL или код) — замер против baseline (§7.3).
4. **Ступень rerank:** cross-encoder поверх top-50. Два пути на выбор: (а) Python-микросервис FastAPI + bge-reranker (заодно — первый Python-сервис в проде твоего стенда), (б) hosted rerank-API. Замер (§7.4).
5. **RBAC на ретриве** (§8.7): гриф на **документе** (доступ определяется документом, до чанка доезжает джойном) + **Row-Level Security** в Postgres, роли из Keycloak-токена. Приложение подключается под `app_user` из М0 — под суперпользователем политика не фильтрует ничего и молча. Тесты: предохранитель «подключены НЕ суперпользователем» (без него остальные зеленеют по ложной причине); низкопривилегированный пользователь не получает защищённый чанк ни при каком запросе; recall с включённым фильтром не упал (§8.6).
6. **Удаление и tombstone (§8.3):** удали документ «по требованию субъекта» — убедись, что он ушёл из выдачи, и посмотри, что физически осталось в индексе.

**DoD:** таблица метрик по ступеням лестницы (naive → hybrid → +rerank) на золотом наборе; все три RLS-теста в CI (включая предохранитель); конвейер собран в `RetrievalService` — его переиспользуют М4 и М5; записка «на какой ступени остановился и почему» (мини-ADR, с отклонёнными альтернативами).

## Модуль 4 — Агенты и оркестрация

**Читай:** гл. 10–14. **Цель:** агент как распределённая система — твоя фора; сделать её явной. **Детализация:** `course/module-4.md`.

1. **Свой харнесс: ReAct-цикл вручную** (чистая Java, без фреймворка, ~150 строк): Thought → Action → Observation над 2–3 инструментами (поиск по KB из М3, статус заказа — заглушка). То, что ты пишешь, и есть **харнесс** (§10.2) — детерминированная половина агента: сбор контекста, парсинг вызовов, исполнение, состояние, бюджеты. Прочувствуй его до того, как фреймворк его спрячет; агент = LLM-ядро + вот этот твой код.
2. **Лимиты и детекция прогресса** (§10.5): бюджет итераций/токенов + повтор сигнатуры (tool + хэш аргументов) → прерывание с эскалацией. Тест: инструмент, возвращающий бесполезный ответ, — агент останавливается, а не крутится.
3. **Orchestrator-Workers (§11.5), надёжность — дисциплиной саги.** Канонический паттерн — Orchestrator-Workers (Anthropic); сага Ричардсона здесь — реализационная дисциплина его механики (журнал шагов, идемпотентность шага по ключу, тайм-ауты, компенсации), причём с двумя отличиями, которые книга называет явно: координатор недетерминирован, план динамический. Реализуй на своей таблице саг (прозрачнее для учебных целей; eventuate-tram остаётся опцией). Затем **хаос-эксперимент** (chaos engineering — канон инженерии надёжности, Netflix, principlesofchaos.org; fault injection — общий приём; книга покрывает механику частичных отказов в §10.4–10.6, не вводя этого имени): убей воркер после его side effect, но до завершения саги — докат вперёд идемпотентен (второй заявки не появилось), откат компенсирует сделанное; оба сценария — автотестом.
4. **Human-in-the-Loop Gate по карточке §10.6:** очередь ревью, карточка решения (что/почему/предпросмотр), безопасный тайм-аут, журнал, метрики (доля одобрений, время решения). Затем сымитируй **automation complacency** — каноническое имя деградации человеческого надзора (Parasuraman & Riley, 1997; разговорно — rubber-stamping): одобряй всё подряд не глядя, 30–50 действий, — метрика гейта обязана это детектировать (доля → 100%, время решения → секунды).
5. **Workflow против агента** на одной задаче (§10.3, §11.8): та же задача фиксированной цепочкой и автономным циклом — стоимость/латентность/предсказуемость, вывод для прода.
6. **Разбор отказа по MAST** (§14.4): возьми 3 сбойные траектории из своих логов и классифицируй по таксономии.

**DoD:** Orchestrator-Workers-агент с зелёным хаос-тестом (chaos engineering); гейт с работающей метрикой automation complacency; сравнительная таблица workflow/agent; 3 разбора отказов по MAST; 10–20 размеченных задач «запрос → ожидаемый инструмент» — пойдут в eval-гейт М6 (проверка «верный инструмент» — §17.5; сам eval-гейт — §17.8).

## Модуль 5 — MCP и JVM-фреймворки

**Читай:** гл. 15–16. **Цель:** интеграция как стандарт, и оба стиля JVM-стека руками. **Детализация:** `course/module-5.md`.

1. **MCP-сервер на Spring AI** (серверные инструменты через `@McpTool` — ветка Spring AI 1.1+; на 1.0 GA — `@Tool` + `MethodToolCallbackProvider`, сверь с версией BOM из М0): `search_kb`, `get_order_status`, `create_ticket` — обёртки над М3/М4. У создания заявки третий параметр не факультативен: `createTicket(category, summary, stepKey)` — ключ шага саги (п. 3 М4) доезжает до эффекта только через сигнатуру инструмента, и подставляет его харнесс перед вызовом, затирая написанное моделью. Подключи к любому MCP-хосту (Claude Desktop/CLI) и посмотри вызовы своих инструментов «чужой» моделью — ключ там придумывает модель и дедупликации нет: это цена демонстрации.
2. **Свой MCP-клиент** (`spring-ai-starter-mcp-client`) — вторая половина модуля, не факультатив: переведи харнесс М4 на инструменты **только** через него, убрав прямые вызовы сервисов. Чужой хост — чёрный ящик: одобрение инструментов, `tools/list` и подгрузка методик живут внутри него и руками не трогаются. Со своим клиентом твой харнесс становится полноценным хостом (раскладка ролей — §15.2), и на этом звене висят пиннинг (п. 6), замер skill (п. 7) и сборка М8.
3. **OAuth на MCP** через Keycloak (§15.7): сервер как OAuth Resource Server; тест — вызов без токена/с чужим scope отклоняется. Затем шаг идентичности агента (§15.7, Deep Dive): вместо сквозного проброса пользовательского токена — **token exchange** (RFC 8693, в Keycloak включается на клиенте) с сужением scope; в спанах Langfuse — оба субъекта: кто инициировал (пользователь) и что исполняло (агент как NHI). Твоя Keycloak-экспертиза встречается с новым периметром.
4. **Тот же ассистент на LangChain4j AiServices** (интерфейс + `@Tool` + `@MemoryId`): сравни с Advisors-стилем Spring AI — §16.3 руками; двухстраничная записка «что где композируется».
5. **Блокирование event loop под нагрузкой** (§16.5): вызови модель блокирующе внутри WebFlux-обработчика под нагрузкой (wrk/gatling) — посмотри деградацию; вынеси на boundedElastic/виртуальные потоки — сравни p99.
6. **Rug pull руками** (§15.7; канонический термин безопасности MCP — подмена определения инструмента после одобрения): в этой модели угроз атакующий — **сервер**, поэтому подмену ты играешь за него, а контрмеру ставишь на противоположной стороне. Измени описание одобренного инструмента — зафиксируй, что хост этого не заметил; прикрути пиннинг одобренных описаний по хешу **в своём MCP-клиенте** (п. 2). Саму меру даёт §15.7 («Одобренные описания инструментов фиксируют по хешу»), сторону она не называет — её выводит курс из §15.2 и Прил. D: доверенная граница — хост, сервер потенциально недоверен.
7. **Skills и code execution (§12.6).** (а) Оформи методику «как эскалировать заявку» как **skill**: каталог со `SKILL.md` (имя + описание в заголовке, инструкции в теле, шаблон письма отдельным файлом). Трёхступенчатую подгрузку реализуй **в своём харнессе М4**: skill — механика хоста, а не MCP-сервера, через сервер её не подключить, а в чужом хосте не потрогать. Замер progressive disclosure — по Langfuse своего харнесса, три числа: методика вшита в системный промпт; skill подключён, но вопрос не про эскалацию; вопрос про эскалацию. Тот же каталог в Claude Desktop — необязательное «посмотреть глазами»: чисел оттуда не снять, твой Langfuse в чужой хост не видит. (б) **Code mode**: задача «закрой все заявки старше 30 дней с уведомлением» — сначала петлёй tool calling (N ходов), затем одним сгенерированным скриптом над файловыми обёртками тех же инструментов; сравни токены, ходы и латентность. Санитарное правило: сгенерированный код исполняется только в контейнере без маршрута наружу (§19.6) — «без сети наружу» ≠ «без сети вообще».

**DoD:** защищённый OAuth MCP-сервер с token exchange, к которому подключается внешний хост; харнесс М4 ходит за инструментами только через свой MCP-клиент, прямых вызовов сервисов не осталось (звено сборки М8); записка-сравнение двух фреймворков; график p99 до/после выноса блокирующего вызова; rug pull воспроизведён и пойман пиннингом по хешу в своём клиенте (тест зелёный); замер «skill против вшитого промпта» (три числа) и «code mode против петли» с числами.

## Модуль 6 — Продакшен: evals, наблюдаемость, безопасность, стоимость

**Читай:** гл. 17–20 (+ Deep Dive о классификаторе в §2.2 и PII-контур §25.4). **Цель:** превратить стенд в систему, которой можно доверять. **Детализация:** `course/module-6.md`.

1. **Eval-гейт в CI** (§17.8): золотой набор из М3 + детерминированные проверки (валидность схем, верный инструмент) + LLM-судья с рубрикой; порог — красный билд. Инструмент — DeepEval (Python) или promptfoo (Node/TS, YAML-конфиг).
2. **Смещения судьи руками** (§17.4): 20 пар ответов, каждая в обоих порядках — измерь позиционное смещение своего судьи; посчитай каппу судьи против своей разметки (§9.4). Судья не откалиброван — числам веры нет.
3. **Размер выборки** (§17.7): по формуле реши, сколько примеров нужно, чтобы отличить 90% от 85% — сверь со своим набором и честно запиши, что твои 50 ловят только грубые регрессии.
4. **Red-team по чек-листу §19.7:** косвенная инъекция через документ в корпусе RAG (инструкция эксфильтрации в регламенте), композиция «чтение + исходящий вызов» (§12.5, lethal trifecta), попытка обойти RBAC через промпт. Каждую атаку — в тест, каждый пробой — в фикс (обособление, taint-правило, gate).
5. **Трассы и стоимость:** дерево спанов агента в Langfuse сверь с Приложением C; атрибуция стоимости по функции/пользователю (§18.5); кэш-эксперимент — вынеси системный промпт в кэшируемый префикс и подтверди экономику §20.2 замером.
6. **Тонкий LLM-шлюз (§20.6):** проведи все вызовы модели через единую точку выхода — маршрутизация, квота с деградацией вместо 500, учёт токенов на вызывающего. Не полноценный governance-слой (§25.3), а тот минимум точки контроля, который капстоун (М8) переиспользует как готовый шлюз.
7. **Классификатор-маршрутизатор с измеренным отказом (§2.2, Deep Dive):** в шлюзе — роутинг «простое → локальная/дешёвая, сложное → сильная» (классификатор: начни с эвристики, затем дешёвый LLM-вызов со structured output). Калибруй порог по матрице цен ошибок, а не по accuracy. Главный эксперимент — **молчаливый отказ**: подсунь категорию запросов, которой не было в разметке, и покажи (числом по маршрутам в Langfuse), что без офлайн-eval ты дрейф не заметил; затем заведи алерт на распределение маршрутов.
8. **PII-контур (§25.4):** обнаружение на входе в индекс и на выходе шлюза — Presidio (или свой каскад regex + NER, для русского возьми русскоязычную NER-модель). 30 размеченных фрагментов с русскими сущностями (имена, телефоны, ИНН): измерь recall и precision; отдельно зафиксируй, что англоязычный дефолт молча пропускает кириллические имена. Порог сдвигай в recall на исходящем направлении — и посмотри глазами, во что превращаются ответы при перестраховке (цена false positive).

**DoD:** CI падает на подсунутой регрессии промпта; отчёт red-team (атаки → пробои → фиксы → повторный прогон зелёный); дашборд стоимости на пользователя; все вызовы модели идут через тонкий шлюз; маршрутизатор с алертом на дрейф и PII-контур с измеренными recall и precision (по экземплярам сущностей, не по типам).
